# Lessons Learned

> **Rule:** Every non-trivial bug fix or unexpected behavior gets an entry here.  
> **Format:** Table rows, newest at top.

| Date | Category | Lesson | Root Cause | Prevention |
|------|----------|--------|------------|------------|
| 2026-04-12 | safety | **`mapped_coverage ?? 1.0` violated the hard safety rule: "NEVER display safe when mapped_coverage < 0.3".** When a product's `mappedCoverage` was null in the DB, the fallback of `1.0` (optimistic) meant `UnknownIngredientBanner` never fired and `_ScoreExplainerCard` displayed "Strong overall quality" for products whose ingredients were never mapped. This is a medical-grade false-safety signal. The `_ScoreExplainerCard` also lacked a `mappedCoverage >= 0.3` guard in its show-condition, compounding the issue. | Convenience-driven default: developer picked `1.0` to mean "don't show the banner" for null rows, but null means "unknown coverage" which is the WORST case in a safety context. The explainer card was added later without checking the existing safety rules. | **For medical-grade apps, ALWAYS default to the conservative value.** `mappedCoverage ?? 0.0` (assume worst). Any new widget that displays a positive quality/safety signal must check `mappedCoverage >= 0.3` in its show-condition. Add this check to the code review template. |
| 2026-04-12 | safety | **`on Object` catch silently swallowed logic errors in personalized interaction warnings.** `_loadPersonalizedInteractions` caught `Object` (including `StateError`, `AssertionError`, `OutOfMemoryError`) because the `interactionDatabaseProvider` throws `UnimplementedError` in tests. This meant a real Drift bug at runtime would be swallowed and the user would see no interaction warnings — a silent safety failure. | Test behavior leaked into production error handling. The provider stub pattern (`throw UnimplementedError('must be overridden')`) requires the consumer to catch `Error`, but catching `Error` in production is a Dart anti-pattern because it hides real bugs. | **NEVER widen a catch clause to accommodate test infrastructure.** Use specific catches: `on UnimplementedError` for the test stub + `on Exception` for real runtime errors. Better yet: override the provider in tests properly so the stub never throws. |
| 2026-04-12 | safety | **Quick Check "No interactions" green card appeared on DB errors AND empty fingerprints.** The `_runPairCheck` method returned `const []` for three distinct reasons: (1) no interactions found (genuinely clean), (2) one/both fingerprints empty (check never ran), (3) DB threw an exception (catch set `_results = const []`). All three showed the same green "safe to take together" card — a false-safety signal for cases 2 and 3. | Single-state result design: `List<InteractionResult>?` cannot distinguish "clean" from "error" from "insufficient data". The catch block set `_results` to empty instead of a separate error state. | **Every medical safety check needs 3 distinct UI states:** success (clean), error (check failed), and insufficient-data (check couldn't run). Use separate booleans (`_checkError`, `_insufficientData`) or a sealed result type. NEVER show a positive safety claim when the check didn't actually complete. |
| 2026-04-12 | correctness | **`_canonicalIdsForProduct` in `stack_providers.dart` omitted `.toLowerCase()` — causing silent missed interaction warnings.** Three other call sites (`product_detail_screen.dart`, `quick_check_screen.dart`, `stack_interaction_checker.dart._normalizeCanonicalIds`) all lowercased canonical IDs. The provider helper did not. Any canonical ID with mixed case in `ingredient_fingerprint` JSON silently failed to match the normalized IDs in the interaction DB. No crash, no error — just missed warnings. | Copy-paste divergence. The helper was written separately from the checker's normalize function and skipped the lowercase step. No shared utility function for canonical ID extraction. | **Extract shared logic into a single function.** All canonical ID extraction should go through one `normalizeCanonicalIds()` utility, not 4 separate implementations. Add a test that verifies canonical IDs are lowercased after extraction. grep for `.keys.map` across the codebase to find other extraction sites that might diverge. |
| 2026-04-12 | correctness | **`RecalledIngredientViolation.bannerMessage` crashed on empty `commonNames` list.** Called `.first` on `commonNames` without checking `isNotEmpty`. The JSON field `common_names` can be `[]` or absent, producing an empty list. `StateError: No element` crashed the stack tab's recall banner. | Assumed the data was always well-formed. The `commonNames` field was populated from optional JSON, but the getter assumed at least one entry. | **ALWAYS guard `.first` and `.last` with `.isNotEmpty` checks.** For data from JSON/external sources, assume every field can be empty/null regardless of what the schema says. Fallback to `canonicalId` or a generic label when display names are missing. |
| 2026-04-12 | perf | **`FutureBuilder` inside a `ConsumerWidget` re-creates its Future on every rebuild.** `_RecallAlertSlot` called `_findRecalledProducts(coreDb)` directly in `build()`, creating a new Future every time any ancestor rebuilt. On a stack of 10 entries, this was 10 sequential DB queries per rebuild cycle. The canonical `recalledIngredientsReportProvider` already existed but wasn't used. | The widget was written as a quick prototype without checking if a provider already existed for the same data. FutureBuilder identifies futures by reference, so a new future = a new loading cycle. | **NEVER create Futures inside build().** Check if a Riverpod provider already computes the data you need. If you must use FutureBuilder, cache the Future in a field (via StatefulWidget) so it's created once, not per-rebuild. Prefer Riverpod `AsyncValue.when()` over `FutureBuilder` in ConsumerWidgets. |
| 2026-04-12 | perf | **Stack safety score ignored synergy bonuses — `StackSafetyScorer` called without `synergies` parameter.** The scorer formula is `100 - penalties + synergy_bonuses`, but `_StackSummaryCard` called `compute(issues: allIssues)` without passing synergies (default `const []`). `synergyReportProvider` was added in the same sprint specifically to compute those bonuses, but the wiring was missed. Users with known synergy clusters (Vitamin D + K2) saw the same score as users without. | The scorer and the synergy provider were implemented in separate commits. The wiring step was overlooked because the scorer "worked" (compiled, returned a score) without synergies — it just returned a systematically understated score. | **When adding a new data source to an existing computation, search for ALL call sites of the computation and wire the new data.** grep for `StackSafetyScorer` or `compute(issues:` to find every consumer. Add a test that verifies the score changes when synergies are present. |
| 2026-04-12 | arch | **`SynergyReport.isEmpty` and `RecalledIngredientsReport.isEmpty` were stored fields that could diverge from `matches.isEmpty`.** Both classes stored `final bool isEmpty` alongside the list, set at construction time. A constructor call with mismatched values (e.g., `isEmpty: true` with a non-empty list) would create an inconsistent object. | Defensive design instinct to "cache" a simple boolean. But for a `final` list field, `matches.isEmpty` is O(1) anyway — no performance reason to store it separately. | **Make `isEmpty` a computed getter, not a stored field**, for any class where it's derivable from other fields. `bool get isEmpty => matches.isEmpty;` eliminates the invariant risk with zero cost. Same pattern applies to `isNotEmpty`, `length`, etc. |
| 2026-04-12 | arch | **Handoff file was stale — M3 (Flutter interaction DB binding) was listed as incomplete but was actually 100% done.** The handoff from the previous session listed M3 tasks as "remaining" (build_runner, bundle artifact, wire provider, verify lookups), but all were already shipped. Three reader agents were launched to verify before discovering everything was already wired. | The handoff was written before the final commits of the previous session, and the session ended before updating it. The agent wrote the handoff based on the plan, not the actual git state. | **ALWAYS verify handoff claims against `git log` and file existence before acting on them.** Run `flutter analyze` + `flutter test` immediately. Don't trust task checklists — trust the codebase. A 5-minute verification pass saves hours of re-implementation. |
| 2026-04-12 | process | **Sprint Tracker sprint numbers diverged from the master roadmap.** The original `2026-04-07-flutter-complete-roadmap-design.md` defined Sprints 0-30 linearly across V1.0-V3.1. During implementation, sprints were renumbered (M1-M5 milestones, Sprint 17-21 for tech debt/features), creating confusion about what was done vs planned. 9 major features from the roadmap were never added to the tracker. | Organic sprint creation during implementation without cross-referencing the master roadmap. No process to reconcile the two documents. | **After every sprint is completed, cross-reference the master roadmap for features that should have been tracked but weren't.** Maintain a "Future Releases" section in the tracker with explicit version assignments (V1.0/V1.1/V2.0) so nothing falls through the cracks. |
| 2026-04-12 | testing | **`pumpAndSettle()` hangs forever when ANY Riverpod provider fires an async Drift DB call during widget init.** This includes `profileProvider.loadFromDb()`, `FutureBuilder` with DB queries, `ConsumerStatefulWidget.initState()` calling async DB methods, and `scrollUntilVisible()` (which calls `pumpAndSettle` internally). The fix is a 3-part pattern: (1) replace `pumpAndSettle()` with `pump()` + `pump(Duration(milliseconds: 100))`, (2) replace `scrollUntilVisible()` with manual `drag()` + `pump()` loops, (3) create/close DBs inside each test body (NOT `setUp`/`tearDown` — Drift's `close()` hangs when called from `tearDown` after the fake-async zone drains). This pattern fixed 10 tests across 3 files (`app_test.dart`, `home_screen_test.dart`, `settings_screen_test.dart`). | `pumpAndSettle` loops until no pending frames. Async DB operations (`customSelect`, `loadFromDb`, `getRecentScans`) schedule microtasks that trigger `setState` rebuilds, which schedule new frames — creating an infinite settle loop. `tearDown(() async => db.close())` runs after the fake-async zone tears down, and Drift's `close()` blocks waiting for stream events the zone will never deliver, causing SIGTERM after ~90s. | **Test pattern for ANY screen that touches Drift providers:** `final coreDb = CoreDatabase.memory(); final userDb = UserDatabase.memory();` → `ProviderScope(overrides: [coreDatabaseProvider.overrideWithValue(coreDb), userDatabaseProvider.overrideWithValue(userDb)])` → `pump()` + `pump(100ms)` instead of `pumpAndSettle` → `pumpWidget(SizedBox.shrink()); await db.close();` at end of test body. Copy the medication_entry_screen_test.dart pattern — it was the only file that already did this correctly. |
| 2026-04-12 | arch | **FTS5 virtual table existed in the pipeline output but Flutter search used LIKE.** The pipeline's `build_final_db.py` creates a `products_fts` FTS5 table with porter stemming over `product_name` and `brand_name`, but `CoreDatabase.searchProducts()` used `LIKE '%query%'` — a full table scan that returned UPC duplicates and had no ranking. Switching to `SELECT p.* FROM products_fts f JOIN products_core p ON p.rowid = f.rowid WHERE products_fts MATCH ? ORDER BY rank` made search instant, ranked, and dedup-aware. Always add a LIKE fallback in a try/catch for older DBs without the FTS table. | The FTS table was added to the pipeline months before anyone wired it into the Flutter query layer. No test or lint caught the unused table. The `searchProducts` method was written when FTS didn't exist yet, and was never updated. | When adding a performance optimization to the pipeline (FTS, indexes, materialized views), immediately file a task to wire the consumer. Add a test that queries the FTS table to catch regressions. Document which pipeline tables are "consumed" vs "available but unused." |
| 2026-04-12 | data | **DSLD registers the same physical product multiple times** across years under different `dsld_id`s but the same UPC barcode (e.g., Thorne "5-MTHF 1 mg" appeared 8 times). This caused duplicate search results and confused scanner lookups. Fix: `dedup_by_upc()` in the build pipeline groups by normalized UPC, keeps the best row (active > discontinued, highest score, newest dsld_id), deletes losers. Scanner path (`findByUpc`) already handled this via `LIMIT 1` + `ORDER BY active, score DESC`, but search path (`searchProducts`) returned all duplicates. | DSLD is a regulatory registry, not a product catalog — it tracks every formulation revision as a separate entry. The pipeline ingested all of them without dedup. | Run `SELECT upc_norm, COUNT(*) FROM products_core GROUP BY upc_norm HAVING COUNT(*) > 1` after any pipeline rebuild. The `dedup_by_upc()` function should be part of every build flow. If new data sources are added, check for similar multi-registration patterns before ingesting. |
| 2026-04-11 | security | Medications stored in `user_stacks_local` (rows where `type='medication'`) are PHI and must NEVER reach Supabase sync. Enforce with a build-time grep test that fails the build if any sync code path touches those rows. | Easy to leak PHI by extending an existing sync path that already handles supplements in the same table. The unified-table design (supplements + meds in one table) trades implementation simplicity for sync risk. | Build-time assertion in `test/release_gate/`: `grep -r "type='medication'" lib/data/supabase/ && exit 1`. Add an ADR documenting the rule. Code review checklist: any change that adds a Supabase sync read must explicitly state how it filters out medication rows. |
| 2026-04-11 | data | supp.ai is an extractive evidence corpus, NOT a curated interaction set. The 59,096 pairs in `sentence_dict.json` are co-occurrences from PubMed abstracts with raw sentence text and paper IDs — they have NO severity, mechanism, or management fields. Treat supp.ai as a secondary "research_pairs" table for citation/evidence backstop, never as a warning source. | Misread supp.ai's branding ("supplement interaction database") as implying curated interactions. The actual files are: cui_metadata (4,910 entities), interaction_id_dict (which pairs co-occur), sentence_dict (the raw extracted text), paper_metadata (168k PubMed papers). | Always inspect the actual file structure of an external dataset before specifying how it integrates. Two-tier data model: curated `interactions` table for warnings, supp.ai `research_pairs` table for "research available" info chips. |
| 2026-04-11 | arch | Flutter `detail_blob` lives in Supabase Storage, not in the bundled `pharmaguide_core.db`. The bundled DB has only `detail_blob_sha256` as a resolver key. Any new feature that reads detail blobs must be async and cache-first via `DetailBlobService.fetchDetailBlobByHash`. | Spec assumed detail blobs were inline columns. They are not — they're per-product JSON files in the `detail-blobs` Supabase Storage bucket at path `{first_2_chars}/{sha256}.json`. Local cache lives in `user_data.db` with a 24-hour TTL. | Pure aggregation functions stay sync. The Riverpod loader provider handles the async + cache-first fetch. Document the data path in any new spec that touches detail blobs. |
| 2026-04-11 | data | `e1_dosage_calculator.dart` reads field names that DO NOT EXIST in `rda_optimal_uls.json`. It reads `entry['nutrient']` (real field: `standard_name`), `group['age_bracket']` (real field: `age_range`), `group['rda']` / `group['ai']` (real field: `rda_ai`). All RDA lookups silently fall through to the `highest_ul` fallback, breaking per-product RDA tier scoring. | Pipeline schema drift between when E1DosageCalculator was written and when `rda_optimal_uls.json` v5.0 was finalized. No contract test caught the mismatch because the calculator silently returned baseline scores. | Schema contract tests: a test that loads the real reference data and asserts `_findNutrientEntry` returns non-null for at least 10 known nutrients. Stack UL Checker (M1) deliberately reads the correct field names — see `lib/services/stack/stack_ul_checker.dart` for the reference implementation. |
| 2026-04-11 | ux | Real-data Section A max in v1.3.x scoring was 21/25 — ZERO products hit the ceiling. Raising A1.max from 15 to 18 (stop compressing the enricher's 0-18 raw score) pushed top products from 21 to 25 and the catalog max score_80 from ~50 to 68.5 (+37%). The ceiling was never the bottleneck; the sub-cap math was. | Spec proposed raising the section max without checking real-data ceilings. The instinct "products are hitting the ceiling, raise it" was wrong — products were nowhere near the ceiling because A1 was silently rescaling 0-18 to 0-15. | Always inspect real data distributions before changing scoring scales. Run `SELECT MAX, AVG, percentiles FROM products_core` first. If <5% of products are within 10% of the ceiling, the ceiling is not the bottleneck. |
| 2026-04-11 | testing | Unit conflict detection in nutrient aggregation must NEVER silent-convert. First-seen unit wins for the sum, mismatched contributions stay in the contribution list with `hasUnitConflict: true`. The UI surfaces the conflict, the math drops the conflicting rows. Silent mg-to-mcg conversion is exactly how medical-grade bugs ship (a 1000× error in either direction). | Convenience-driven design temptation to "just convert mcg to mg automatically." A single buggy entry in the unit lookup table would multiply real doses by 1000. | Aggregator design: never call any unit conversion function. If two products report a nutrient in different units, flag and skip-the-non-canonical. Leave conversion to a future, deliberately-built unit normalization pipeline (with its own tests). |
| 2026-04-11 | arch | Flutter already had `Severity` enum (5 tiers), `InteractionResult` model, `StackInteractionChecker` (119 LOC), and `UserStacksLocal` table with `type='medication'` + `rxcui` + `drug_classes` columns BEFORE the v2.0 interaction spec was written. Always inspect existing primitives before specifying new ones. | Subagent wrote the spec without reading the Flutter repo. Result was a 978-line spec that over-engineered primitives that already existed and missed the existing infrastructure entirely. | Any new spec for an existing area MUST start with a "What already exists" section grounded in real file/line references. Run an exploration subagent FIRST, before drafting the spec. |
| 2026-04-08 | data | Pre-built SQLite DB from pipeline may lack columns defined in Drift schema. Drift crashes with "Null check operator used on a null value" when mapping rows with missing columns. Always add a beforeOpen migration that ALTERs missing columns into existence. | Pipeline exported 61 columns but Drift table defined 88 (v1.3.0 additions not yet in pipeline). Drift generated non-nullable reads for columns that didn't exist in the file. | Add _ensureV130Columns() in CoreDatabase.migration.beforeOpen that runs ALTER TABLE ADD COLUMN IF NOT EXISTS for every v1.3.0 column. Make all pipeline-populated integer flags nullable() instead of withDefault(). |
| 2026-04-08 | data | SyncService bucket name and path must match actual Supabase Storage layout. The DB was in bucket "pharmaguide" at path "v{version}/pharmaguide_core.db", not bucket "databases" at root. | Hardcoded bucket name and flat path didn't match versioned storage structure. First-launch download silently failed. | Read export_manifest.db_version to build the correct storage path. Always verify bucket/path against actual Supabase Storage before hardcoding. |
| 2026-04-08 | ui | Hardcoded Color(0xFF...) values bypass the design system and break dark mode. Static AppColors fields are light-only. | 7+ files used const Color(0xFF0A7D6F) instead of AppTheme.brandTeal. AppColors had no dark-mode awareness. | Use AppTheme.brandTeal for brand color. Added AppColors.of(context) for theme-aware semantic colors. grep for raw hex on every review. |
| 2026-04-08 | ui | AnimatedOpacity in a conditionally-rendered widget (if _show) never animates — the widget is removed from tree before fade-out plays. | Scanner flash overlay wrapped in if (_showFlash) meant AnimatedOpacity was always opacity=1.0 when in tree. | Keep animated widgets always in tree. Use IgnorePointer(ignoring: !show) + AnimatedOpacity to allow fade in/out. |
| 2026-04-08 | arch | Riverpod providers wrapping async resources (DBs, sockets) must be overridden at startup in ProviderScope — never leave them throwing UnimplementedError at runtime. Any screen that reads the provider before the override is set will crash silently. | coreDatabaseProvider was declared but never wired in main.dart, so every screen that called ref.read(coreDatabaseProvider) threw at runtime. | Always wire new providers in main.dart immediately after declaring them. Add a smoke test that builds the app widget and verifies no UnimplementedError is thrown on first pump. |
| 2026-04-08 | testing | Widget tests that read an uninitialized Riverpod provider cause pumpAndSettle() to time out (not throw) — the test hangs instead of failing fast. | coreDatabaseProvider threw UnimplementedError inside a FutureBuilder, which Flutter swallowed as a build error and kept retrying. pumpAndSettle waited forever for the widget tree to settle. | For widget tests of screens that use DB providers: either (a) override the provider with a mock in the test's ProviderScope, or (b) test only the UI states that don't trigger the DB call. |
| 2026-04-08 | arch | Flutter secrets must be injected via --dart-define at build time (String.fromEnvironment), not read from a .env file at runtime. Runtime .env files can be extracted from the APK by decompiling assets. | Initial plan considered flutter_dotenv for runtime key loading. | Always use --dart-define for secrets. Put a Makefile target that reads .env and passes the flags — never let the app binary load the .env file directly. |
| 2026-04-08 | security | Supabase anon key is safe to ship in a mobile binary — RLS enforces per-user access. The service_role key bypasses ALL RLS and must never leave server-side environments (pipeline CI, Edge Functions). They are different keys even though they share the same SUPABASE_URL. | Confusion about whether pipeline and Flutter app share the same keys. | Document clearly: same URL, different key type. Anon key → mobile app. Service role key → pipeline/CI/Edge Functions only. |
| 2026-04-08 | wiring | LIKE-based full-text search (product_name LIKE '%query%') is sufficient for a 180K product catalog when there is no FTS virtual table. FTS (sqlite_fts5) would be faster but requires the pipeline to pre-build the FTS table. LIKE works without any pipeline changes. | Sprint tracker claimed FTS search but the pipeline DB had no FTS table. | Before specifying FTS, verify the DB actually has the virtual table. If not, LIKE is a safe fallback — document the tradeoff (O(n) vs O(log n)) in the ADR. |
| 2026-04-07 | data | 9 of 14 conditions in clinical_risk_taxonomy had zero interaction rules. Never claim a feature works without verifying data coverage. | Assumed all taxonomy entries had corresponding interaction data written. Only 5 conditions (diabetes, hypertension, kidney disease, liver disease, pregnancy) had rules. | Before building UI for a data-driven feature, query the actual data and count non-null entries. Add a coverage gate test that fails if coverage drops below expected threshold. |
| 2026-04-07 | arch | Drug class checklist must stay in profile setup for V1.0. The E2c scoring section in ScoreFitCalculator needs drug classes to compute interaction penalties. Cannot derive from stack until V1.1 when stack-to-drug-class mapping is built. | Suggestion to remove manual drug class entry to simplify profile UX. But no automated alternative existed yet. | Tag profile fields with their consumers. Before removing any profile field, grep for all references and verify each consumer has an alternative data source. |
| 2026-04-07 | data | Never batch-fix JSON data files. Fix one entry at a time, verify each change, run targeted tests after each edit. Batch operations skip entries and introduce silent errors. | Batch update script processed entries sequentially, hit an error on entry 47, continued without reporting, leaving entries 48-143 in an inconsistent state. | Use single-entry update functions. Run the targeted test for that entry immediately after writing. Never use loops that continue-on-error for medical data. |
| 2026-04-07 | data | Always verify API enrichment results case-by-case before writing to data files. Bulk application of API results causes plant/compound collapses and preparation mismatches. | UMLS CUI verification returned the parent compound CUI instead of the specific preparation CUI. Bulk write applied the wrong CUI to 12 entries before anyone noticed. | API enrichment results go into a staging file first. Each entry is reviewed (by human or verification script) before promoting to the canonical data file. |
