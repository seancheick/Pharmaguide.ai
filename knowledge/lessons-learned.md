| 2026-04-16 | safety | **Derived medical-grade user-facing copy is a silent safety footgun — NEVER let a Flutter-side template produce warning text from upstream prose.** Sprint 27.5 shipped a `warning_message` field derived at remap time via the template `"{standard_name} is {status}: {first sentence of reason}"`. An audit of all 139 recall entries found ~30–40 were medically wrong. The worst class: prescription drugs flagged as undeclared adulterants (metformin, meloxicam, sibutramine, sildenafil, tadalafil) rendered as "Metformin is banned: Metformin is a prescription antidiabetic drug..." — inverting the safety signal. A patient on prescribed metformin reads the app and believes their medication was just banned. Everything else (orange_b, ephedra, DMAA) was encyclopedic definition, not a warning. Root cause: `reason.split('. ')[0]` returns an *encyclopedic definition sentence*, not a *risk sentence* — two structurally different types of text. No Flutter-side template can bridge that gap. Fix (Sprint 27.6 Path A): dropped `warning_message` from asset + model + provider + test; banner now composes from structured fields only (`statusLabel + productName + commonNames`). Real fix (Path C, owned upstream): pipeline authors three new fields with safety-team review — `ban_context` enum (`substance` / `adulterant_in_supplements` / `watchlist` / `export_restricted`), `safety_warning` (≤200 chars), `safety_warning_one_liner` (≤80 chars, banner form). Build-time validator rejects any string that starts with `"{standard_name} is"` — catches re-derivation attempts. | Convenience: producing medical text from structured fields is "cheap" in the remap. But medical text is not a structured-field derivation problem — it's an authoring problem. Single template, no review gate, no validator, no safety-team sign-off. Two different types of text (definition vs warning) were assumed interchangeable. | **NEVER derive medical-grade user-facing strings from upstream prose in a remap.** All such strings must be authored upstream with safety-team review and passed through verbatim. Add negative assertions in contract tests for any removed derived field: `expect(first.containsKey('warning_message'), isFalse, reason: 'see Sprint 27.6')` — so a future accidental re-derivation fails loud. Add pipeline-side build-time validator rules (starts-with check, length bounds, required action verb) to reject encyclopedic openers. Track the authoring review as an explicit sprint task with per-entry checklist — no bulk AI generation, no "draft now, review later." |
| 2026-04-16 | safety | **`status: banned` is a semantic overload — four distinct real-world cases render to one UI banner.** The recall list conflates: (1) *substance bans* (DMAA, ephedra — the molecule is controlled/illegal), (2) *adulterant-in-supplements* (metformin, meloxicam — legitimate prescription drugs found undeclared in supplements; using them as prescribed is fine), (3) *watchlist* (FDA warning letters, no formal ban), (4) *export-restricted* (banned in EU/CA/AU but not US). Conflating case 1 and case 2 is the dangerous part — they need opposite user-facing copy. Case 1: "stop immediately." Case 2: "stop the supplement, KEEP your prescription." A single `status` string cannot carry that distinction. User caught this during review ("metformin is banned? Not as a medication, only as adulterant in supplements"). Fix: Path C adds a `ban_context` enum with those four values; Flutter copy branches on enum, not on substring match. | Original schema overloaded `status` because the 10-entry Flutter v1.0 list happened to be all substance-class bans — adulterant cases came in later with the pipeline v5.0 expansion to 139 entries, and the UI copy rule wasn't updated. No review step forced the question "does this status value still mean the same thing?" when entries were added. | **When an enum-shaped field accumulates new entries, re-audit the UI copy rule every time cardinality doubles.** Don't reuse a single string for semantically-distinct cases. Design rule for any safety-adjacent enum: if a human reviewer can name more than one "meaning" for the same value, split the field. Flutter-side lesson: branch user-facing copy on structured enums, never on free-text substring match (no `if (status.contains('adulterant'))`). |
| 2026-04-16 | testing | **Integration tests for scan→flag paths must inject canned payloads, not load real bundled assets.** Sprint 27.6 added `test/features/stack/recalled_ingredient_integration_test.dart` covering the product-contains-ingredient match. First draft loaded the real `banned_recalled_ingredients.json` — tests would have been tied to production data (139 entries today, different tomorrow), slow, and prone to churn every time the data file changed. Final design: boot `CoreDatabase.memory()` + `UserDatabase.memory()`, seed one product row + one stack entry, override `referenceDataRepositoryProvider` with a `_FakeReferenceDataRepository` returning a 1-entry canned payload, assert the provider future returns the violation. Required a tiny refactor in `stack_safety_providers.dart` — switched `ReferenceDataRepository()` to `ref.watch(referenceDataRepositoryProvider)` so the override works. Tests run <50ms each, fully deterministic, test the match logic not the data. | Default instinct: "use the real data so the test is realistic." But realism ≠ correctness. A test that loads production data tests production data + match logic; when it breaks, you don't know which failed. A test that loads a fixture tests match logic only. Both have value — but the unit-level scan→flag test is the second kind. | **Every medical safety check gets an integration test that injects a minimum viable fixture via a provider override — not one that loads the bundled asset.** Pattern: in-memory DB + 1 seeded row + fake repo via `overrideWith` + `ProviderContainer.read(provider.future)` + assert shape. Asset-loading tests belong in `test/core/*_contract_test.dart` as schema guards, not in feature integration tests. If a provider instantiates a repo with `new`, refactor it to read via `ref.watch` so tests can override — the refactor is tiny and opens the test door. |
| 2026-04-16 | testing | **Negative assertions (`expect(containsKey, isFalse)`) are the right pattern for removed fields in contract tests.** When Sprint 27.6 Path A dropped `warning_message`, the contract test replaced `expect(first, containsPair('warning_message', ...))` with `expect(first.containsKey('warning_message'), isFalse, reason: 'see Sprint 27.6 Path C')`. If a future remap silently re-derives `warning_message` from `reason` — the exact footgun that triggered the Sprint 27.6 cleanup — the test fails loud with a citation to the sprint doc. This is "never let the footgun reappear" enforcement, not just "assert current state." Same pattern applies to any deprecated/removed field, deleted asset key, or renamed enum value. | Contract tests usually assert *positive* state (field X exists, value Y matches). Removal of a field is silently forgotten by the test — if someone re-adds it, no test fails. But re-addition is exactly the regression class that matters for fields removed for *safety* reasons. | **When removing a field from an asset or model for safety/correctness reasons, add a negative assertion in the contract test with a reason citation.** Format: `expect(first.containsKey('fieldName'), isFalse, reason: 'See SPRINT_TRACKER Sprint 27.6 — re-introduction requires pipeline-side authoring, not Flutter-side derivation.')`. This converts institutional memory into test enforcement. Apply to: deprecated API fields, removed columns, deleted enum values, replaced computation paths. |
| 2026-04-16 | safety | **`contains_*` hazard flags need documented derivation provenance per flag — otherwise every flag is a silent-accuracy risk.** The export schema has booleans like `contains_stimulants`, `contains_sedatives`, `contains_blood_thinners`, `contains_omega3`, `contains_probiotics`, `contains_collagen`, `contains_adaptogens`, `contains_nootropics`. For each flag, the pipeline must answer: what's the source-of-truth list? (keyword file? IQM tag join? manual map?) Where is it versioned? What's the gold-standard test set? Is the derivation case-insensitive? What happens on unknown ingredients — silent `false` or error? For safety-critical flags (`contains_blood_thinners`, `contains_stimulants`), auto-derivation is a risk — curation is required. No crash possible, only silent misclassification (e.g., a stimulant-containing product flagged as non-stimulant misses the stack-safety check). Handoff to pipeline repo (`docs/HANDOFF_PIPELINE_SAFETY_DATA.md`) lists the six-footgun audit. | Flags shipped incrementally over multiple sprints without a unified provenance doc. Each dev who added a flag documented it in their own PR, but there's no central "source-of-truth per flag" table. No failing test would catch a regression in derivation accuracy — only user-visible missing warnings would. | **Every `contains_*` / hazard-class boolean flag gets a row in a central `docs/safety-flags-provenance.md` (or pipeline-side equivalent) listing: source list file, derivation method (keyword/tag-join/manual), test set, last-audited date, owner.** Every flag needs a gold-standard test set in the pipeline test suite (≥20 known-positive + ≥20 known-negative products). For safety-critical flags, audit quarterly against clinical literature. Unknown-ingredient default: log + `false`, never silent `false`. |
| 2026-04-16 | safety | **Bundled reference-data assets are Flutter-schema-owned, NOT pipeline-synced. Direct-copying a pipeline JSON over a Flutter asset silently wipes the feature.** `synergy_cluster.json` and `banned_recalled_ingredients.json` had been on Flutter v1.0 schema (keys `clusters` / `recalled_ingredients`) while the pipeline emitted v5.0 (keys `synergy_clusters` / `ingredients`). A well-meaning future dev who "refreshes" the asset by copying the pipeline file in place would change the top-level key. Every consumer reading `clustersData['clusters']` or `recallData['recalled_ingredients']` would get `null`, fall through to `.map((e) => ...)` over an empty list (because of null-safe `??`), and render zero synergy bonuses + zero recall warnings — no crash, no log, no user-visible error. Medical-grade app, silent-safety failure. Fix: wrote a v5.0→Flutter-v1.1 transform (58 synergy + 139 recall entries with pipeline-to-Flutter field rename table, evidence-tier int→string map, severity enum map, `regulatory_basis`/`warning_message` derivations with safety-review flag in `_metadata`) AND a `test/core/reference_data_contract_test.dart` that asserts the Flutter key IS present AND the pipeline key is NOT. | Asset files look like data — "just a JSON refresh" — so contributors don't realize the schema is intentionally different. Consumer code uses `?? const []` defensively, which means schema drift silently degrades to "no data" instead of throwing. No contract test existed before this sprint. | **Every bundled JSON asset that diverges from its upstream source needs three things: (1) a `_metadata.schema_version` field, (2) a remap script (or documented transform rules) checked into the pipeline repo, (3) a contract test under `test/core/` that asserts both the expected top-level key IS present AND the upstream-source key is NOT present.** The "NOT present" assertion is the critical one — it's what catches a direct-copy accident. Same pattern applies to `rda_optimal_uls.json`, `timing_rules.json`, `medication_depletions.json` if they ever diverge from pipeline format. |
| 2026-04-16 | safety | **Derived medical-grade fields in an asset remap need an explicit `_metadata.migration_note` review flag, not a silent best-effort default.** The synergy/recall remap produced 139 `warning_message` strings with the template `"{standard_name} is {status}: {first sentence of reason}"` and 53 `bonus_points` values indexed on evidence_tier (strong→2, moderate/limited→1). Both asset files now carry a `_metadata.migration_note` naming the derived fields explicitly. | Medical-grade fields exist in Flutter that have no pipeline source because the Flutter asset was hand-crafted in 2025 while the pipeline v5.0 schema was designed independently. Bridging the gap requires judgment — but "judgment" in an automated transform means either pick-the-conservative-default or fabricate. Both are dangerous without a review trail. | **Every derived field in a remap must be flagged in `_metadata.migration_note` with the derivation formula, AND the spec must list which fields need human review before a production release.** Do NOT auto-generate medical-grade user-facing text in a migration without a review gate. | 2026-04-16 | arch | **Release-gate file-scan tests must track renamed source files.** After splitting `stack_providers.dart` into `active_stack_provider.dart` + 3 siblings (with the original path kept as a barrel re-export), `test/release_gate/phi_medication_no_sync_test.dart` kept reading from the barrel path — which no longer contained the `StackActions.addMedication` method body. | 2026-04-16 | arch | **Barrel re-export pattern makes file splits a zero-risk refactor.** Splitting a large file (`home_screen.dart` 1345 LOC, `stack_providers.dart`, `pipeline_detail_sections.dart`) into a thin shell + multiple focused files risks breaking every call-site that imports the original path. Keeping the original file as a barrel (`export 'split_file.dart';`) decouples the physical split from the call-site migration — external imports don't change, the split can land in one PR, and call-site cleanup becomes an optional follow-up. Exception: the file must still be physically read by any release-gate regex test (see the release-gate lesson above). | Forcing every call-site to update at the same time as the split makes the diff huge, risky, and often blocks on unrelated concerns (test refactors, circular imports). The refactor gets deferred and the file keeps growing. | Standard recipe for any file >500 LOC: (1) extract the logical sub-units into new files with clear public APIs, (2) leave the original path as a `library; export ...;` barrel listing each split, (3) keep private widgets co-located with their sole consumer (underscore prefix), (4) audit `test/release_gate/` for any regex scans pointing at the original path and update them to the new physical files. |
| 2026-04-16 | arch | **Blob fetch extraction: `FutureProvider.family.autoDispose` replaces `ConsumerState` async plumbing.** `product_detail_screen.dart` carried `_detailBlob` / `_blobLoading` / `_blobError` / `_cacheTtl` fields plus a `_loadDetailBlob()` method (~54 lines) that did cache-check → SHA-256 lookup → Supabase fetch → cache-write. Moving that whole flow into a `FutureProvider.family.autoDispose<Map?, String>` keyed on `dsldId` eliminated the fields, shrunk the screen, and made retry a one-liner (`ref.invalidate(detailBlobProvider(widget.dsldId))`). Autodispose ensures navigating away frees the cached AsyncValue. Service dependency (`DetailBlobService`) is a separate provider so tests override it cleanly. | `ConsumerState` async fields are the default path of least resistance — any dev adding a new async fetch reaches for `initState` + `setState`, not a provider. The state then proliferates (loading/error/data/retry) and the widget grows. No one splits until the file crosses a pain threshold. | When an async fetch is keyed on a widget prop (dsldId, userId, productId): start with `FutureProvider.family.autoDispose`, not state. Extract the service it depends on into its own `Provider<T>` so tests can override. The widget derives 3 locals (`blobAsync.asData?.value`, `blobAsync.isLoading`, `blobAsync.hasError`) from a single `ref.watch`. Retry is `ref.invalidate(provider(key))`.
